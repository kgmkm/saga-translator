# Hermes／Windows での実行時の注意

saga-translator を Hermes Agent（Windows 11 の git-bash）で動かすときの実践的な注意。
レビュー §2-9・§P0-6 の指摘に基づく。

## 原則

- **不要なインライン生成（`python3 -c`・heredoc）を減らし、`.py` ファイル経由で実行する。**
  インラインのコードや heredoc は Hermes の承認待ちで止まることがある。
  スクリプト（`scripts/*.py`）を直接呼べば承認は発生しない。
- **探索は `maxdepth` と対象ディレクトリを限定する。**
  作業ドライブ（`Y:` など）が SMB の場合、全ツリーへの再帰探索（無指定の `find`／`grep -r`）は
  タイムアウトする。探索範囲は必ず `_saga/<作品ID>/` または `_翻訳版/<作品ID>/` まで絞る。
- **1コマンドの標準出力は 2KB 以下に留める。**
  大量の出力（ファイル一覧・全文ダンプ）を stdout に出すと、会話キャッシュに積もって
  以後の全コールで再読され、コンテキストを圧迫する（s0 ではキャッシュ再読が 1,337 万トークンに達した）。
  代わりに `_work/logs/` にファイルとして出力し、stdout には要約だけを出す。

## 承認の実績

以下の承認待ちが実際に発生した。無駄な待ちを減らすには、インラインの生成を避けるのが最も効果的。

| セッション | 件数 | 実害 |
|---|---|---|
| s0 | 2回（計約4分） | `python3 -c` のインラインコードで承認待ち |
| s3 | タイムアウト7回 | heredoc・インライン生成が承認待ちでタイムアウト。再実行の原因に |

必要な承認（年齢確認・安全規則・権限）は決して回避しない。承認の待ち時間は工程時間と
**分けて計測する**（待ち時間そのものは、以後の設計判断の資料になる）。

## 具体的なコツ

- **大量の grep／find を打つ前に、対象を絞る。**
  例：全作品横断の代わりに `_saga/<作品ID>/analysis/characters-*.toml` だけを対象にする。
- **文字コードは UTF-8（BOM なし・LF 改行）を維持する。**
  Windows 標準のメモ帳で開くときは文字化けしない。CRLF が混入すると TOML パーサーや
  regex の `$` アンカーがずれる（実例：`analysis_done_at` の重複ガード無効化）。
- **長いリストは `_work/logs/` 下にファイルとして出し、stdout には要約のみを出す。**
  - 良い例：`[ingest] work: ... / title: ... / paras: 123 / chars: 45678`
  - 悪い例：全段落の原文を stdout にダンプする

## 他ハーネス・長文書き込みの注意（レビュー #13・#14 / H 節）

- **goose / PowerShell 等でも読まれる前提で書く**: `python -c` のインライン実行は PowerShell では引用符の解釈が衝突する（`python -c "..."` が壊れる）。検証や小処理は**一時 .py ファイルに書いて実行**する（Hermes でもインラインは承認プロンプトを呼びやすい）。コマンド例は必ず POSIX シェル（git-bash）と .py ファイルの両方で通る形にする。
- **長文の書き込みは分割し、書いた後に確かめる**: 4000字級を1回で書くとハーネスの書き込みが落ちることがある（write_file のタイムアウト、内容の混線・重複の実例あり）。分割して書き、**書いた後に内容のハッシュか行数を確認**してから次へ進む。
