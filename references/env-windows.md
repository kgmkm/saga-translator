# env-windows — Windows での実行時の注意

saga-translator を Windows（git-bash・PowerShell 等）で動かすときの実践的な注意。
ハーネス固有の事項は「Hermes 節」に分離した。レビュー §2-9・§P0-6 の指摘に基づく。

## 原則

- **不要なインライン生成（`python3 -c`・heredoc）を減らし、`.py` ファイル経由で実行する。**
  インラインのコードや heredoc はハーネスの承認待ちで止まることがある。
  スクリプト（`scripts/*.py`）を直接呼べば承認は発生しない。
- **探索は `maxdepth` と対象ディレクトリを限定する。**
  作業ドライブ（`Y:` など）が SMB の場合、全ツリーへの再帰探索（無指定の `find`／`grep -r`）は
  タイムアウトする。探索範囲は必ず `_saga/<作品ID>/` または `_翻訳版/<作品ID>/` まで絞る。
- **1コマンドの標準出力は 2KB 以下に留める。**
  大量の出力（ファイル一覧・全文ダンプ）を stdout に出すと、会話キャッシュに積もって
  以後の全コールで再読され、コンテキストを圧迫する（実測は「Hermes 節」）。
  代わりに `_work/logs/` にファイルとして出力し、stdout には要約だけを出す。

## PowerShell

- **成功判定は exit コードではなく出力本文で行う。**
  python が stderr へ書くと、PowerShell が NativeCommandError として扱い、成功でも
  exit 1 に見えることがある（実害あり）。判定は出力本文（例: `[commit] align: PASS`）で行う。
- **文字コード**: 実行前に `$env:PYTHONIOENCODING='utf-8'` を設定する。
- **長文はファイル経由**: `python -c "…"` は引用符の解釈が衝突する。検証や小処理は
  一時 `.py` ファイルに書いて実行する。
- **`Set-Content -Encoding utf8` は BOM を付けることがある。** BOM（先頭の `EF BB BF`）が
  入ると TOML パーサーが先頭で落ちる。書き込み後は先頭バイトを確認する。
- **非 ASCII パスは `-LiteralPath`** で扱う（ワイルドカード解釈による誤解決を避ける）。
- **`python3` が無い環境がある**（DSH 同梱ランタイム等）。まず実体（`python` / `py -3` 等）を
  確定し、コマンド例の `python3` は環境に合わせて読み替える。

## git-bash

- コマンド例は必ず POSIX シェル（git-bash）と `.py` ファイルの両方で通る形にする。

## Hermes 節

Hermes Agent（Windows 11 の git-bash）で動かすときの固有事項。

**インライン生成は承認待ちを呼びやすい。** 以下の承認待ちが実際に発生した。無駄な待ちを減らすには、インラインの生成を避けるのが最も効果的。

| セッション | 件数 | 実害 |
|---|---|---|
| s0 | 2回（計約4分） | `python3 -c` のインラインコードで承認待ち |
| s3 | タイムアウト7回 | heredoc・インライン生成が承認待ちでタイムアウト。再実行の原因に |

必要な承認（年齢確認・安全規則・権限）は決して回避しない。承認の待ち時間は工程時間と
**分けて計測する**（待ち時間そのものは、以後の設計判断の資料になる）。

- **stdout 絞り込みの実測**: 大量の出力を stdout に出すと会話キャッシュに積もって以後の
  全コールで再読され、コンテキストを圧迫する（s0 ではキャッシュ再読が 1,337 万トークンに達した）。

## 具体的なコツ

- **大量の grep／find を打つ前に、対象を絞る。**
  例：全作品横断の代わりに `_saga/<作品ID>/analysis/characters-*.toml` だけを対象にする。
- **文字コードは UTF-8（BOM なし・LF 改行）を維持する。**
  Windows 標準のメモ帳で開くときは文字化けしない。CRLF が混入すると TOML パーサーや
  regex の `$` アンカーがずれる（実例：`analysis_done_at` の重複ガード無効化）。
- **長いリストは `_work/logs/` 下にファイルとして出し、stdout には要約のみを出す。**
  - 良い例：`[ingest] work: ... / title: ... / paras: 123 / chars: 45678`
  - 悪い例：全段落の原文を stdout にダンプする

## goose 等の他ハーネス（レビュー #13）

- **goose / PowerShell 等でも読まれる前提で書く**: `python -c` のインライン実行は PowerShell では引用符の解釈が衝突する（`python -c "..."` が壊れる）。検証や小処理は**一時 .py ファイルに書いて実行**する（Hermes でもインラインは承認プロンプトを呼びやすい）。

## 長文書き込みの注意（レビュー #14）

- **長文の書き込みは分割し、書いた後に確かめる**: 4000字級を1回で書くとハーネスの書き込みが落ちることがある（write_file のタイムアウト、内容の混線・重複の実例あり）。分割して書き、**書いた後に内容のハッシュか行数を確認**してから次へ進む。
